Why this demo exists

A bus-arrival app needs two things to actually ship:

  • Good predictions — how close the “bus arrives in X minutes” message is to reality.
  • To fit on the device — the prediction model runs on a cheap, battery-powered computer inside the bus (or on a phone). That computer has strict limits: not too much CPU, memory, battery or network.

Researchers often only report accuracy. A brilliant model that drains the battery in an hour never makes it to a real bus. The paper this demo is based on proposes a Guideline Layer: a lightweight watch-dog that sits next to the model, measures these four limits on every single prediction, and shouts when one is broken.

The four modules of the Guideline Layer

1

Monitoring Engine

guideline_layer/monitoring.py

After every prediction, samples the four resources. Measures what a laptop can measure for real (time per prediction, model size on disk) and models what happens on the target device (an embedded computer).

Example reading: model = 0.9 MB · 8 ms per prediction

2

Threshold Checker

guideline_layer/thresholds.py

Compares each reading against the four benchmarks proposed in the paper. No opinion, just a comparison: is CPU above 30%? Is the model bigger than 500 MB?

Checks: CPU ≤ 30% · RAM ≤ 500 MB · battery ≤ 20%/hr · bandwidth ≤ 1 MB/min

3

Warning System

guideline_layer/warnings.py

If a limit is broken, raises an alert with a concrete fix (“CPU too high — prune the model or use a lighter one”). A cooldown stops the same alert from spamming, and repeated breaches escalate to critical.

432 alerts instead of 1,728 noisy violations in the reference run

4

Logging Module

guideline_layer/logging_module.py

Writes one lightweight log line per prediction and periodically “syncs” a summary to a cloud server (simulated by a local file) — the history an operator needs to spot slow resource leaks.

The closed loop — what happens at every single stop

1 · Observe

The bus reaches a stop → the model predicts the remaining minutes → the Monitoring Engine samples CPU, RAM, battery, bandwidth.

→
2 · Compare

The Threshold Checker compares each sample to the paper’s four limits.

→
3 · Act

If a limit is broken, the Warning System raises an alert that says what and how to fix it.

→
4 · Log

Everything is logged; every 10th prediction is synced to the simulated cloud.

The prediction model is never modified. The layer only watches — that is the paper’s central claim, and the Live Run tab shows it happening in real time.

Words you will see, explained

ETA — Estimated Time of Arrival

The “bus arrives in X minutes” figure passengers see. Here the model predicts the remaining minutes to the end of the route at every stop.

MAE — the way we score predictions

Mean Absolute Error: the average size of the mistake in seconds, ignoring direction. “MAE 34 s” = a typical prediction is off by about half a minute. Lower is better.

CPU 30% limit — why a number out of nowhere?

The paper proposes 30% as a sane sustained-CPU ceiling for a small embedded device that also has to run the bus’s other software. It is a starting point you tune per device, not a law.

Why is CPU “modelled” and not measured?

This demo runs on a laptop, whose math libraries make even big neural networks look trivially fast. So the simulator estimates each model’s real compute cost (multiply–accumulate operations) and converts it to the CPU load the same model would cause on the paper’s target device class. Raw laptop timings are still logged — look in the Logs tab.

Cooldown

If a limit stays broken for 100 stops, the layer does not send 100 alerts — it alerts once, then waits 2 minutes (simulated) before alerting again. Repeated breaches escalate to critical.

Quantization / pruning — the suggested fixes

Quantization shrinks a model by storing its numbers with less precision (e.g. int8 instead of float32) → less RAM. Pruning removes connections the model barely uses → less CPU. Both are standard “make the model smaller” tricks the Warning System recommends.

What is “the cloud” here?

A simulated fleet server: log summaries are written to a local CSV that stands in for uploads to a real cloud. The Logs tab shows the files.

Is the data real?

The trips are synthetic but generated from a physics-based model of a bus corridor (segment lengths, speeds, peak-hour traffic, weather). It is ideal for mechanism demos: everything is reproducible with a fixed seed.

Where each model lands

Good = bottom-right-ish is a lie… let’s be precise: accurate models should sit low (small error). The green zone is accurate and under the CPU ceiling — that is where a model is deployable. The red zone is accurate but too hungry for the device.

What the layer caught

Violations = single predictions that broke a limit. Alerts = the messages actually sent after the cooldown deduplicates them. Log records = everything written to disk.

Honest limitations

  • Synthetic data — trips come from a seeded physics-based generator, not real GPS feeds. Numbers will shift run to run.
  • Modelled device resources — CPU and battery are estimated for the paper’s embedded target device from the models’ structure. Raw per-prediction timings are measured for real on this laptop and logged.
  • Layer overhead ≈ 0 — measured in the CLI experiments (the layer only adds checks + a log line per prediction); it is not re-measured in every dashboard run to keep the demo fast.
