Cyber-Physical Digital Twin for Smart Transportation

A true Digital Twin links a Physical Asset to a Synchronized Virtual Model via a Bi-directional Closed Loop. This platform implements a dual-state Digital Twin for public transit under limited infrastructure:

  • Transit Physical Twin (Spatial State): Mirrors the real bus's location, speed, and stop arrivals along the 32 km ISCON ↔ PDPU corridor, generating dynamic arrival estimates (ETA).
  • Edge Hardware Twin (Cyber-Physical State): Virtualizes the on-board IoT computer (Android / ESP32 unit), continuously tracking sustained CPU load, memory footprint, battery drain, and cellular bandwidth.
  • Closed-Loop Guard Layer (Actuation): Prevents edge hardware exhaustion by evaluating operational benchmarks (e.g. CPU ≤ 30%) and issuing real-time remediation directives (model pruning, quantization, or switching to lightweight models).

The Three Pillars of This Digital Twin

Pillar 1 · Physical Entity

Physical Asset & Sensors

The real-world transit vehicle operating along the Ahmedabad–Gandhinagar corridor, equipped with an on-board IoT tracking node, GPS receiver, tri-axial accelerometer, and cellular antenna.

Feeds: 1–2 Hz real GPS packets, velocity, and timestamp logs.

Pillar 2 · Digital Shadow

Dual-State Virtual Replica

Software models running in synchrony with the bus: spatial route geometry (15 stops), dynamic machine learning ETA predictors (Linear, GBDT, MLP), and virtualized hardware thermal/compute emulators.

Computes: Travel time predictions + per-inference compute MACs.

Pillar 3 · Closed Loop

Guideline Layer Actuation

Continuous closed-loop feedback engine that supervises device limits. If deep models exceed device capacity, it triggers automated alerts and directives to re-configure the edge workload.

Enforces: CPU ≤ 30% · RAM ≤ 500 MB · Battery ≤ 20%/hr · BW ≤ 1 MB/min.

The Four Closed-Loop Modules

1

Monitoring Engine

guideline_layer/monitoring.py

Ingests real-time telemetry from every inference cycle. Measures actual execution wall-time and model footprint, and models sustained hardware strain for embedded chipsets.

Output: Per-inference CPU load, RAM allocation, and network bytes.

2

Threshold Checker

guideline_layer/thresholds.py

Evaluates virtual telemetry against operational bounds (CPU ≤ 30%, RAM ≤ 500 MB, Battery ≤ 20%/hr, Bandwidth ≤ 1 MB/min) to detect micro-level bottlenecks.

Checks: CPU ceiling (30%) · Thermal budget · Cellular quota.

3

Warning System

guideline_layer/warnings.py

Acts as the digital twin's control signal: issues prescriptive remediation directives (INT8 quantization, pruning, or model fallback) with cooldown deduplication.

Action: "CPU exceeded 30% ceiling — switch to Gradient Boosting".

4

Logging Module

guideline_layer/logging_module.py

Maintains high-fidelity JSONL telemetry records on-device and synchronizes batched summaries with the cloud fleet twin for fleet-wide analytics.

Writes: results/dashboard/logs/*.jsonl and cloud syncs.

Key Architectural Concepts

Why is this a Digital Twin and not just a tracking app?

A simple tracker only shows where an object is on a map. A Digital Twin creates a high-fidelity virtual representation of both the physical process (bus movement and arrival times) and the physical asset's cyber-physical state (CPU, memory, battery, temperature), connecting them via closed-loop feedback.

Spatial Twin vs. Hardware Twin

The Spatial Twin simulates route progression, traffic delays, and ETAs. The Hardware Twin simulates on-board computational health, ensuring the predictive model does not drain the vehicle's battery or crash the microprocessor.

Why is the 30% CPU ceiling critical?

On resource-constrained embedded edge devices (e.g. Raspberry Pi, ESP32, or vehicle tracking units), the microprocessor must concurrently handle ticketing, GPS ingestion, passenger counting, and radio communication. Exceeding 30% CPU causes thermal throttling, task queue backpressure, and system freezes.

Dataset Authenticity

The default data source is the real empirical ISCON–PDPU transit corridor dataset from Ahmedabad, India (36 recorded trips across 15 physical stops). Synthetic physics-based simulation is also available for stress-testing.
